## 2. Understand the Problem

A UK energy utility purchases electricity from the wholesale market.

Its purchasing team needs to understand how reliable wind generation forecasts were during January 2026, using the information available when purchasing decisions would have been made.

Wind generation can vary. Forecasts may overestimate or underestimate the actual electricity generated by wind farms.

The company wants a dashboard that helps its team:

- Review wind generation forecasts.
- Understand when forecasts were published.
- Compare forecasts with actual wind generation.
- Identify forecast errors and patterns.
- Evaluate forecast accuracy throughout January 2026.
- Understand the uncertainty associated with wind generation forecasts when making purchasing decisions.

### The central business problem

How accurately did Elexon's wind generation forecasts predict actual wind generation during January 2026, considering only forecasts available at the relevant decision time?

### Important business limitations

The application does not receive the company's actual electricity purchase transactions, purchase quantities, transaction prices, total demand, or complete portfolio data.

Therefore:

- Do not invent historical purchasing decisions.
- Do not claim to know how much electricity the company actually purchased.
- Do not claim that forecast errors directly caused specific purchases.
- Do not calculate imaginary financial savings or losses.
- Do not claim to calculate the optimal electricity purchase quantity.
- Present forecast analysis as decision support, not as a complete electricity trading system.

## 6. Elexon Data Integration

Use only the datasets specified in the challenge.

### Actual wind generation

Dataset: `FUELHH`

Documentation:

https://bmrs.elexon.co.uk/api-documentation/endpoint/datasets/FUELHH/stream

Filter the data using:

`fuelType = "WIND"`

Relevant fields:

- `startTime`
- `generation`

### Wind generation forecasts

Dataset: `WINDFOR`

Documentation:

https://bmrs.elexon.co.uk/api-documentation/endpoint/datasets/WINDFOR/stream

Relevant fields:

- `startTime`
- `publishTime`
- `generation`

Use the documented endpoint parameters and response schemas. Inspect the actual API responses before writing assumptions into the code.

### Date scope

The evaluation period is January 1–31, 2026, inclusive.

Use half-hour delivery periods, with 48 periods per complete day.

Treat all market timestamps carefully. Use UK local time for user-facing dates and times, including the correct GMT/BST offset where applicable. Store and compare timestamps consistently internally. Do not assume that every timestamp string uses the same timezone format.

### Critical forecast-selection rule

The app must not compare actual generation with a forecast published after the relevant decision cutoff.

For each delivery interval:

1. Identify the interval's `startTime`.
2. Determine the relevant decision cutoff according to the configured decision-time assumption.
3. Find forecasts for that delivery interval published at or before the cutoff.
4. Select the most recent eligible forecast.
5. Compare that forecast with the corresponding actual generation.
6. Record the selected `publishTime` so users can inspect why that forecast was used.

If the business has not specified a precise purchasing decision cutoff, make it configurable and document the default as an assumption, not an established fact about the client.

Do not invent a decision cutoff and present it as confirmed business policy.

### Historical data validation

Before building the analysis, verify that the Elexon API provides the historical records required to reconstruct January 2026 forecasts and their publication times.

Check pagination, query parameters, rate limits, response structure, missing records, and historical availability.

If the API does not preserve all necessary historical forecast versions, document the limitation and implement the best honest fallback.

Do not pretend that the latest available forecast can reconstruct what was known historically.

If historical forecast data is incomplete, clearly identify affected periods and exclude them from accuracy calculations where appropriate.

Do not silently treat missing values as zero.

### API efficiency

- Request only the required data and date range.
- Avoid repeatedly fetching identical data.
- Use a simple in-memory cache with a documented expiry if helpful.
- Handle timeouts, HTTP errors, invalid responses, and rate limits.
- Do not make the frontend call Elexon directly.
- Keep API integration logic separate from business calculations.

No API keys should be hardcoded.

## 7. Forecast Accuracy Calculations

Implement these metrics using actual forecasts selected according to the decision cutoff.

### Mean Absolute Error (MAE)

Average absolute difference between forecast and actual generation.

`MAE = mean(abs(forecast - actual))`

Lower is better.

### Root Mean Squared Error (RMSE)

Square root of the average squared difference between forecast and actual generation.

`RMSE = sqrt(mean((forecast - actual) ** 2))`

Lower is better. Large errors receive more weight.

### Forecast bias

Average signed difference:

`Bias = mean(forecast - actual)`

- Positive bias means forecasts tended to overestimate generation.
- Negative bias means forecasts tended to underestimate generation.
- A value near zero means little average signed error, but does not necessarily mean individual forecasts were accurate.

### Optional additional metrics

Add percentage-based error only if it can be calculated responsibly. Actual generation can be zero or close to zero, making percentage errors misleading or undefined.

Always:

- State the unit of measurement.
- Explain the metric briefly.
- Exclude invalid or missing pairs appropriately.
- Show the number of valid matched observations.
- Display a useful empty state when insufficient data exists.
- Never display hardcoded accuracy metrics as if they were calculated from real data.

Add unit tests using small, manually verified examples.
